# 结构化 Agent 间通信 · 设计文档（v0.4 最终版，决策用，已冻结）

> **状态：已评估 · 不采纳（2026-08-29）。** 结论：维持现状自由交接（A 臂），不引入结构化交接格式（B/C）。依据 §7.3 决策树：真实任务 A/B/C 三臂 0 编造、信息完整性打平（task2/task3），task1 差距系无工具环境 confound（A 臂去探测代码库扑空，真实环境中会正常作答）；B/C 为加复杂度改动，未明显超过 A → 维持 A。
>
> 文档状态：冻结，不再迭代。v2 真实任务基准结果见文末附录。

## 0. 核心假设（先读这个）

本试点要回答的核心假设**不是**"弱模型能不能产出格式"（大概率能——SenseNova 吐个 markdown 块不难），而是：

> **逼它套格式，会不会让它编造本没有的结构？**

具体表现：为了填满"关键结论""风险/待确认项"等字段，模型把没有的结论编出来、把不存在的风险写上去，以"看起来完成了格式"。这是最可能沉掉方案的风险（见 §10 风险 4），且只有 §6.3 那个贵的基准能抓。

**kill-switch 是必要不充分**：过了只代表格式稳定（块在、字段非空），不代表内容真实。内容真实性靠 §6.3 基准盲评抓。

## 1. 问题

### 1.1 现状基线

OPC 各 Agent 当前靠自由格式 markdown 交接，定义在两处：
- **Director prompt** 的「调度协议」段：Director 调度子 Agent 时写任务描述（自由文本），产出写入 `{{WORK_PATH}}/{任务名}/`
- **各子 Agent prompt** 的「协作接口」段：声明"我需要什么输入/产出给谁"（部分角色具体，部分泛泛）

交接链路：Director 写任务描述 → 子 Agent 读文件 → 产出写文件 → Director 读产出 → 调度下一环。

### 1.2 三类失真（弱模型 SenseNova 上）

| 失真类型 | 表现 | 根因 |
|---|---|---|
| **信息丢失** | Director 调度时漏传上游产出，子 Agent 上下文不全 | 自由文本无强制字段，模型想到什么写什么 |
| **格式漂移** | 每个 Agent 产出结构各异，下一环难稳定消费 | 无统一产出 schema |
| **意图歧义** | 子 Agent 误读任务目标，产出偏离预期 | 任务目标无"一句话结果"强制 |

（advisor 基准已证：弱模型受益于结构脚手架，但过度刚性会让它崩——见 §10 风险 3。）

## 2. 目标与非目标

### 目标
1. Director 每次调度都传齐子 Agent 需要的字段（防信息丢失）
2. 子 Agent 产出可被下一环稳定解析（防格式漂移）
3. 任务目标强制一句话结果（防意图歧义）

### 实现路径（三臂，基准选最优）

本方案不预设"必须用结构化块"，而是通过三臂基准对比，选对弱模型最优的实现：

| 臂 | 实现 | 成本 | 风险 |
|---|---|---|---|
| **A 现状** | 自由文本交接 | 0 | 信息丢失/格式漂移/意图歧义 |
| **B prose 强制** | 不加新块、不加解析层，只把现有「交接协议」6 个字段改成 prose 里强制必填（"必须包含：目标/输入件/约束/验收标准/产出件/风险"） | 低 | 弱模型可能仍漂移，但没有格式可崩、不触发"为填格式而编造" |
| **C 完整 schema** | `## 任务交接 v1` / `## 结果交接 v1` 结构化块 + Director 解析校验层 | 高 | 格式可崩、可能触发"为填字段而编造" |

**核心决策点**：若 B ≈ C（任务完成度差距 < 5%），取 B——对弱模型，强制散文字段可能拿到大部分收益、又没有格式可崩、也不触发编造风险。

### 非目标
- 不追求严格 JSON（弱模型易在严格 JSON 上失败）
- 不追求覆盖所有场景（边缘场景允许"待确认"降级）
- 不一次改全部角色（按角色逐个 gate）
- 不改变现有 `{{WORK_PATH}}/{任务名}/` 文件产出机制（schema 是文件头部的结构层，不是替换文件）

## 3. 设计原则

1. **加法而非替换**：在现有 markdown 产出头部加一层带标签的结构块，不强制纯 JSON
2. **字段最小化**：只保留能挡住真实失真的字段，每个字段都要"挣得自己的位置"
3. **人可读 + 机可解析**：markdown 带标签字段（`## 任务交接` + 列表），不用裸 JSON
4. **可降级**：可选字段未知就写"待确认"，不许编造；必填字段缺失则 Director 打回
5. **版本化**：schema 带版本号，将来演进时可兼容旧产出

## 4. Schema（C 臂完整 schema，仅当基准选中 C 时实施）

### 4.1 任务交接（Director → 子 Agent）

写在 `{{WORK_PATH}}/{任务名}/task.md` 头部，Director 调度时生成。

```markdown
## 任务交接 v1

- **任务类型**: 新功能开发 / bug 修复 / 重构 / 代码审查 / 分析 / 其他
- **目标**: （一句话，描述"完成后长什么样"，不是"做什么"）
- **上游产出摘要**: （前一环的实际结论，1-3 句；无则写"无"）
- **输入件**:
  - `路径/文件1` — （一句话说明是什么）
  - `路径/文件2` — ...
- **约束**: （技术栈/时间/预算/不可改动的部分；无则写"无"）
- **验收标准**: （可验证的完成条件，1-3 条）
- **建议下一步**: （完成后建议交给谁；Director 有最终决定权）

---

（以下为自由文本任务详情，可展开）
```

**字段必填/可选**：

| 字段 | 必填 | 缺失处理 |
|---|---|---|
| 任务类型 | ✅ 必填 | Director 打回，不调度 |
| 目标 | ✅ 必填 | Director 打回，不调度 |
| 输入件 | ✅ 必填（可空列表） | Director 打回 |
| 上游产出摘要 | ⚠️ 可选 | 写"无" |
| 约束 | ⚠️ 可选 | 写"无" |
| 验收标准 | ⚠️ 可选 | 写"待确认"，子 Agent 执行前需追问 |
| 建议下一步 | ⚠️ 可选 | 写"待 Director 决定" |

### 4.2 结果交接（子 Agent → Director）

写在子 Agent 产出文件头部，或 `{{WORK_PATH}}/{任务名}/result.md`。

```markdown
## 结果交接 v1

- **状态**: 完成 / 阻塞 / 待确认
- **产出件**:
  - `路径/文件1` — （一句话说明内容）
  - `路径/文件2` — ...
- **关键结论或决策**: （不只是"分析了"，而是"结论是 X，因为 Y"）
- **风险 / 待确认项**: （浮出来，不埋没；无则写"无"）
- **建议下一步**: （建议交给谁/做什么；Director 有最终决定权）

---

（以下为自由文本产出详情）
```

**字段必填/可选**：

| 字段 | 必填 | 缺失处理 |
|---|---|---|
| 状态 | ✅ 必填 | Director 视为异常，打回 |
| 产出件 | ✅ 必填（可空列表，状态=阻塞时） | Director 打回 |
| 关键结论或决策 | ✅ 必填（状态=完成时） | Director 打回，要求补充 |
| 风险 / 待确认项 | ⚠️ 可选 | 写"无" |
| 建议下一步 | ⚠️ 可选 | 写"待 Director 决定" |

### 4.3 Director 解析/校验规则

1. 收到子 Agent 产出后，先读 `## 结果交接 v1` 块
2. **必填字段缺失** → 打回子 Agent 补充，不进入下一环
3. **状态=阻塞** → Director 读取"风险/待确认项"，决定解除阻塞或升级
4. **状态=待确认** → Director 读取"关键结论"，决定确认或追问
5. 格式无法解析（没有 `## 结果交接 v1` 块）→ 降级为自由文本消费。**试点期**：漂移事件人工观察记录（依赖 C2 指标闭环，当前未实现，见 §10 开放问题 1）；**C2 建成后**：自动记录供 AgentManager 评估。

## 5. 与现有系统的集成方式

### 5.1 改哪里（prompts/ 单源）

| 改动点 | 文件 | 内容 |
|---|---|---|
| Director 调度指令 | `prompts/director.md` | 「调度协议」段增加：调度时必须生成 `## 任务交接 v1` 块，必填字段缺了不调度 |
| 子 Agent 输入解析 | 各子 Agent prompt 的「协作接口」段 | 增加：接收任务时先读 `## 任务交接 v1` 块，必填字段缺失则追问 Director，不硬猜 |
| 子 Agent 产出格式 | 各子 Agent prompt | 增加：产出必须带 `## 结果交接 v1` 块，必填字段缺了不算完成 |

### 5.2 渐进式引入（试点阶段）

试点期（dev 角色）采用**双轨制**（仅 C 臂）：
- Director 同时输出 `## 任务交接 v1` 块 + 原有自由文本任务描述
- Dev 产出同时带 `## 结果交接 v1` 块 + 原有自由文本产出
- 基准测试对比 A/B/C 三臂的产出质量
- 试点通过后，逐步去掉冗余的自由文本部分（或保留为详情展开）

### 5.3 五运行时兼容性

schema 是 markdown 带标签字段，五个运行时（opencode/claude-code/pi/gemini/codex）均消费 markdown，无兼容性问题。codex 的 TOML front matter 不受影响（schema 在正文，不在 front matter）。

## 6. 试点方案（dev，单角色）

### 6.1 第 0 步：格式稳定性 kill-switch（必要不充分）

**目的**：先验证 SenseNova 能不能稳定产出 `## 结果交接 v1` 格式，产不出整个方案原地判死。

**注意**：kill-switch 是**必要不充分**——过了只代表格式稳定（块在、字段非空），不代表内容真实。一个尽职吐块、但把"关键结论"编造出来的模型能过 kill-switch。内容真实性靠 §6.3 基准盲评抓。

**方法**：
- 构造 5 个典型 Dev 任务（见 §6.2）
- 用 SenseNova 跑 Dev 角色，每个任务跑 3 次（N=15 次产出）
- 检查每次产出是否包含 `## 结果交接 v1` 块、必填字段是否非空

**判死阈值**（可调起点，非定论，试点后根据实际数据调整）：
- 15 次中 ≥3 次缺 `## 结果交接 v1` 块 → 格式不稳定，C 臂判死（B 臂仍可继续）
- 15 次中 ≥5 次必填字段缺失 → 字段设计对弱模型太难，简化后重试或判死
- 低于阈值 → 进入第 1 步基准测试

### 6.2 试点任务集（5 个 Dev 典型任务）

| # | 任务类型 | 描述 | 覆盖点 |
|---|---|---|---|
| 1 | 新功能开发 | 给现有项目加一个用户登录功能 | 多输入件、约束、验收标准 |
| 2 | bug 修复 | 修复用户报告的登录页 500 错误 | 上游产出摘要（错误日志）、阻塞场景 |
| 3 | 重构 | 把某个 500 行的函数拆成模块化结构 | 约束（不可改变外部接口）、风险 |
| 4 | 代码审查 | 审查一个 PR 的安全性和可维护性 | 关键结论、风险项、建议下一步 |
| 5 | 分析 | 评估两个第三方库的选型 | 上游产出摘要、决策建议、待确认项 |

### 6.3 第 1 步：三臂基准测试（沿用 advisor 方法论）

**三臂对比**：

| 臂 | 实现 | 说明 |
|---|---|---|
| **A 现状** | 自由文本交接 | 对照组 |
| **B prose 强制** | 不加新块、不加解析层，只把现有「交接协议」6 个字段改成 prose 里强制必填 | 中间更便宜的选项 |
| **C 完整 schema** | `## 任务交接 v1` + `## 结果交接 v1` 结构化块 + Director 解析校验层 | 完整方案 |

**方法**：
- 同一批 5 个任务，三个变体
- 每个变体每个任务跑 3 次（N=5 任务 × 3 变体 × 3 次 = **45 次产出**）
- 强模型盲评配对打分，rubric 见 §7.2

**人力成本**：45 次产出的盲评配对由创始人 + 评审完成，约 1 天工作量（含读产出、配对打分、汇总）。这是本试点最大的真实人力开销。

## 7. 基准闸门（go/no-go）

### 7.1 主判据

三臂中任务完成度最高、且信息丢失类错误最少的臂胜出。不预设 C 一定赢。

### 7.2 盲评 rubric（任务完成度权重 50%）

| 维度 | 权重 | 评分标准 |
|---|---|---|
| **任务完成度** | 50% | 产出是否达到验收标准、能否直接使用 |
| **信息完整性** | 20% | 是否丢失上游产出/输入件中的关键信息（**信息丢失类错误的测量点**） |
| **格式可解析性** | 10% | 下一环能否稳定解析产出（结构块齐全、必填字段有值） |
| **关键结论质量** | 10% | 是否有明确结论/决策，还是只堆"分析了"；**是否编造了不存在的结论**（核心假设测量点） |
| **风险浮出** | 10% | 风险/待确认项是否主动浮出，还是埋没在正文里 |

**信息丢失类错误的测量方法**：盲评者对比任务输入件列表与产出中实际引用/消费的输入件，关键输入件未被消费即记一次"信息丢失"。

**格式开销度量**（事后测量，非模型自我约束）：结构块 token 数 / 产出总 token 数。若 > 15%，说明格式开销挤占了内容空间，需简化字段或回退到 B 臂。弱模型无法边生成边自我约束此比例，只能事后测量。

### 7.3 决策规则（默认落 A，加法不改善不值得加）

**优先级**：先过"是否明显超过 A"这关，过不了一律回 A；过了的才进 B/C 取舍。

**第一步：淘汰**
1. 任一臂盲评中发现 ≥2 次"编造了不存在的结论/风险" → 该臂直接判死（核心假设证伪）
2. 任一臂任务完成度 ≤ A（没超过现状）→ 该臂判死（加法不改善不值得加负担/格式/编造风险）

**第二步：幸存者里选**
- 都没超 A → 维持 A 现状
- 只有 B 超 A → 取 B
- 只有 C 超 A → 取 C
- B、C 都超 A → 默认取 B（便宜、不脆、不触发编造），除非 C 再高出 B ≥5% 才取 C

## 8. 推广判据（仅当试点通过）

1. **一次一个角色**，每个都过同样的"格式稳定性 + 基准质量"检查
2. **优先改交接最含糊/最丢信息的角色**，不是最容易的（dev 试点通过后，下一个应是交接最频繁的角色，由 AgentManager 评估排序）
3. 全部改 `prompts/` 单源 + 重生成五运行时 + CI 漂移校验
4. 推广期保持双轨制（结构块 + 自由文本），全角色通过后再考虑去掉冗余

## 9. 回滚方案

- **试点期**：B/C 臂都是加法，去掉新增指令即回滚到 A 现状（revert commit 即可）
- **推广期**：每个角色独立 commit，回滚单个角色不影响其他角色
- **schema 演进**：版本号（v1）允许新旧共存，Director 可解析 v1 和 v2，旧产出不失效

## 10. 风险与开放问题

| # | 风险 | 缓解 |
|---|---|---|
| 1 | 弱模型产不出结构 | 第 0 步 kill-switch 先挡（§6.1，仅 C 臂） |
| 2 | "看起来美但实际没用" | 基准闸门抓这个（§7） |
| 3 | 过度刚性把弱模型搞崩 | markdown 带标签字段、允许"待确认"、不强制严格 JSON；B 臂无格式可崩 |
| 4 | **弱模型为填字段编造内容**（"待确认"没用，模型直接编） | 盲评 rubric 含"关键结论质量"维度（含编造检测）；决策规则第一步直接判死；B 臂无格式触发编造 |
| 5 | **格式开销挤占输出长度**（advisor 发现的"框架吃掉结论"） | §7.2 事后测量格式开销 >15% 则简化或回退；结构块在头部，结论在正文 |
| 6 | **子 Agent 过度关注格式忽略内容** | 任务完成度权重 50%，格式只占 10%，内容差不会因为格式好而通过 |
| 7 | 多跳交接信息衰减 | 输入件字段保留原始路径引用，不只是摘要；多跳时 Director 可回溯原始文件 |
| 8 | 成本：全量碰 10 个 prompt + Director | 按角色逐个 gate，每个独立可回滚 |

### 开放问题

1. **AgentManager 交接质量评估**（依赖 C2 指标闭环，当前未实现）：格式漂移率、信息丢失率的自动采集当前不可用（user_confirm/rate 只记不消费）。试点期漂移事件人工观察记录；C2 建成后再接入 AgentManager 自动评估。
2. schema 是否需要机器可校验的 JSON Schema（用于 CI 检查产出格式）？——试点后如果格式漂移率高再加
3. 阻塞/待确认状态是否需要触发 Director 的自动升级机制？——当前由 Director 人工判断，暂不自动化

## 11. 给评审者（执行这套的 AI）的四个问题

1. **格式稳定性**：这个交接格式你能稳定产出吗？哪里你会漂移或产不出？（特别是必填字段，你会不会为了填而编造？）
2. **字段冗余/歧义**：哪些字段对你显得冗余或有歧义？"目标"和"验收标准"的边界你分得清吗？
3. **信息丢失点**：你现在的自由交接里，究竟在哪一步真的丢了信息？B 臂（prose 强制必填）和 C 臂（结构化块）哪个更可能打到那个点？
4. **编造倾向**：如果某个字段（如"关键结论""风险"）你其实没有内容可填，你会写"无/待确认"还是会编一个？诚实回答——这决定了 C 臂会不会沉。

## 附录：v2 真实任务基准结果（2026-08-29）

> 实验条件：三臂共享完整 `prompts/dev.md` 底座（5539 字符/272 行），唯一差别 = 追加的交接格式（A 无 / B prose 强制 / C 结构化块）。模型 `sensenova-6.7-flash-lite`，温度 0.7，每臂每任务 2 次，共 18 次。盲评（代号甲乙丙丁戊己，评完揭晓映射）。
